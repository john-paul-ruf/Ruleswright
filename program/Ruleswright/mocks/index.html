headless library · no game UI

Eighteen surfaces, zero screens

Ruleswright ships no UI — its hosts own all presentation. What gets designed here is what a developer sees and copies: the docs, the pack contract, the event stream, the errors, the knobs. Every functional requirement is exercised by at least one surface; each mock is a DX contract, not an implementation target.

◈

Code inside these mocks is API illustrative — the Architect owns final signatures. The pack document shape, event anatomy, error anatomy, and snapshot payloads are contracts.

Foundations

the copy-paste path · the randomness spine · the name-keyed stat model

01 · Quickstart

FR-1 · FR-17 · NFR-DX

The copy-paste path: one theme, one seed — generate a pack, build a character, run three rounds. Every line runnable; every example shows its expected output.

02 · Quickstart, annotated

NFR-DX

The same three steps with the requirements pinned to each line — the reviewer's proof that the doc bar (runnable, expected-output, no I/O) is met clause by clause.

03 · Dice & determinism

FR-1 · FR-14 · NFR-det.

One injectable RNG; structured rolls with purpose and verdict; the dice vocabulary formulas may use; RNG state that travels inside snapshots.

04 · Stats & abilities

FR-5 · FR-3 · FR-14

Name-keyed abilities and saves; derived stats from pack formulas; a character is plain JSON; illegal builds rejected with the rule named.

The pack contracts

one document · the same machinery everywhere

05 · Pack anatomy

FR-2 · FR-19 · FR-23

One JSON document: manifest, rules, content. Overrides merge at load; schemaVersion gates compatibility. Hand-authored packs are first-class citizens.

06 · Progression & multi-class

FR-6 · FR-13

Leveling reads from pack tables; the host awards XP; direct level-set and earned levels validate identically; multi-class and demihuman caps as data.

07 · Conditions

FR-7 · FR-4 · FR-13

Durations, per-condition stacking policies, and restricts teeth — all pack data, all riding the event stream.

08 · Magic — no subsystem

FR-8 · FR-9 · FR-11

Spells are actions: vancian bindings and drain pools on one engine; the slot lifecycle; multi-target, per-target saves, mixed outcomes.

Combat

stepwise · spatially optional · reactive by event

09 · Combat loop

FR-4 · FR-10 · FR-13 · FR-14

Stepwise and resumable: begin turn → declare → resolve → end. Every mutation emits an event carrying why.

10 · Spatial layer

FR-11 · FR-4

Optional positions, adjacency, reach — declared per pack. Theater-of-mind packs pay nothing; single-target and burst are the v1 shapes.

11 · Triggered actions

FR-4 · FR-12 · FR-13

Reactions as data riding the event substrate — the engine offers, the host answers. FR-12 proof 2 lives here.

System & tooling

persistence · failure · generation · consumption

12 · Snapshots & persistence

FR-14 · FR-1 · FR-23

Three independent serializers, RNG state included, loud refusal on mismatch — and an engine that performs no I/O of any kind.

13 · Validation errors

FR-2 · FR-14

The error-card gallery: broken references, duplicates, formula errors, spatial refusals, snapshot mismatch — artifact, path, rule, hint.

14 · Bestiary & encounters

FR-15 · FR-16

Monsters from the same character machinery; one table engine for runtime and compiler; deterministic threat-budget assembly.

15 · Generation pipeline

FR-17 · FR-21

Named stages behind a stable interface; two sample themes, two showcases; byte-identical determinism as the contract.

16 · Theme knobs & composition

FR-18 · FR-20

Themes declare knobs as machine-readable data — any host renders the settings form. Themes compose: base + patches, JSON not code.

17 · Packaging & surfaces

FR-22 · FR-23 · NFR-dep.

Runtime / schema / compiler, separately consumable; the runtime-only bundle is a CI proof, not a promise; one versioning discipline.

18 · API map

all FRs · API illustrative

The whole public library on one page — coverage, not signatures: every functional requirement appears at least once in a callable shape. If the final API can't fit a page, it is too big.

User flows

  1. Docs reader: quickstart → annotated → dice → combat-loop — copy-paste to a live, evented, resumable fight.
  2. Pack author: pack-anatomy → stats → progression → conditions → magic → validation-errors — author content, read located errors.
  3. Theme user: theme-knobs → generation-pipeline → pack-anatomy — knobs → generated pack → single-artifact override.
  4. Systems reader: combat-loop → spatial → triggers → snapshots — the full combat spine end to end.
  5. Evaluator: packaging → api-map — three surfaces, one page of API, the FR coverage table.
