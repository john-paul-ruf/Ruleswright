Five surfaces, zero screens

Ruleswright ships no UI — its hosts own all presentation. What gets designed here is what a developer sees and copies: the docs, the pack contract, the event stream, the errors, the knobs. Each mock is a DX contract, not an implementation target.

◈

Code inside these mocks is API illustrative — the Architect owns final signatures. The pack document shape, event anatomy, and error anatomy are contracts.

Surfaces

01 · Quickstart

FR-1 · FR-17 · NFR-DX

The copy-paste path: one theme, one seed — generate a pack, build a character, run three rounds. Every line runnable; every example shows its expected output.

02 · Pack anatomy

FR-2 · FR-19 · FR-23

One JSON document: manifest, rules, content. Overrides merge at load; schemaVersion gates compatibility. Hand-authored packs are first-class citizens.

03 · Combat loop

FR-4 · FR-10 · FR-13 · FR-14

Stepwise and resumable: begin turn → declare → resolve → end. Every mutation emits an event carrying why. Snapshots carry state, RNG, and pack identity.

04 · Validation errors

FR-2 · FR-14

Bad content is rejected loudly at load: artifact id, JSON path, violated rule, hint. A failing pack is never partially loaded.

05 · Theme knobs & composition

FR-17 · FR-18 · FR-20

Themes declare their knobs as machine-readable data — so any host renders a settings form without knowing the theme. And themes compose: a new theme is JSON with patches, not code.

User flows

  1. Docs reader: quickstart → combat-loop — copy-paste to a live, evented, resumable fight.
  2. Pack author: pack-anatomy → validation-errors — author content, read located errors.
  3. Theme user: theme-knobs → pack-anatomy — knobs → generated pack → single-artifact override.
