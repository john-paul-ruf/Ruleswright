Pack anatomy

The pack is one JSON document — the complete contract between author and runtime. Generated packs and hand-authored packs are the same shape: there is no second-class way to write content.

One document, eight sections

pack.json — top level contract 
{
  "manifest":    { },  // id, schemaVersion, license?, attribution?, knob provenance
  "stats":       { },  // ability names, named saves — the engine stores by string
  "actions":     { },  // action types: cost, validity, effect body
  "formulas":    { },  // derived stats: HP, AC, attack bonus, save targets, pools
  "content":     { },  // classes, races, skills, feats, spells, conditions, equipment
  "progression": { },  // HD, class attack tables, save progressions, vancian slots, caps
  "bestiary":    { },  // statblocks built from the same character machinery
  "tables":      { }   // weighted / ranged / nested lookups — one table engine
}

Every artifact inside is addressable by a stable id — that is what makes overrides possible (FR-19).

The same machinery everywhere

Rules are data, so the shapes rhyme: an action, a spell, and a condition all read like variations of one idea. All names coined (Q7/Q8).

action
{
  "id": "strike",
  "cost": { "slots": {"main": 1} },
  "valid": "hasTarget(adjacent)",
  "effect": { "attack": "melee",
    "onHit": "damage(1d8+str)" }
}
spell — an action + metadata
{
  "id": "grave-light",
  "magic": { "level": 1,
    "lists": ["hexer"] },
  "cost": { "vancian": 1 },
  "effect": { "save": "reason",
    "fail": "condition(dazzed,3)" }
}
condition
{
  "id": "sapped",
  "duration": 3,
  "stacking": "refresh",
  "restricts":
    ["actions.tagged:main"]
}
progression — the classic-CRPG feel lives here, as data
"warden": {
  "hd": "d8",
  "attackTable": [ // descending-AC convention — the engine never knows
    { "level": 1, "ac2": 20, "ac9": 13 },
    { "level": 4, "ac2": 17, "ac9": 10 } ],
  "saves": { "vigor": [0,0,1,1,2], "reason": [0,1,1,2,2] },
  "slots": { "1": [1,2,2,3], "2": [0,1,2,2] }  // vancian, by class level
}

Overrides — the GM's last word

Every artifact is addressable, so a host or GM patches any of them without forking the pack. Overrides merge at load with documented precedence.

overrides.json — patch one artifact
{
  "override": "barrow-wight",
  "patch": {
    "hpBonus": 4,
    "actions.claw.onHit":
      "damage(1d8+2)"
  }
}
✓

Same seed ⇒ byte-identical regeneration, so your edits anchor cleanly every time (FR-19).

◈

Theme composition (FR-20) uses the same patch idea one level up: base theme + patches = new theme. JSON, not code.

schemaVersion — the compatibility contract

▲

Every pack declares schemaVersion; the engine validates compatibility at load. Major bumps are breaking by definition and ship with a written compatibility note. One versioning discipline across packs, overrides, and snapshots — a version bump renders old snapshots stale, and the API says so plainly (FR-14, FR-23).
